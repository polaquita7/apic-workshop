1. Contexto: Qué es Broken Object Level Authorization

En la API de saldos que construímos, se expone el CUIT de la empresa como parámetro de ruta:

GET /saldos/30716595549/obtenersaldo

El CUIT es un dato descifrable y predecible. Sin un control de autorización, cualquier cliente autenticado podría consultar el saldo de cualquier empresa simplemente cambiando el CUIT en la URL. Esta vulnerabilidad se conoce como BOLA (Broken Object Level Authorization): el sistema autentica quién sos, pero no verifica si el recurso que pedís te pertenece.

Antes de este lab Nuestra API es vulnerable GET /saldos/30500010237/obtenersaldo devuelve los datos de Agropecuaria Pampeana aunque el token pertenezca a Constructora del Sur. El backend confía en cualquier llamada que llegue.

La solución: el control pertenece al gateway, no al backend

¿Qué resolvió API Connect?

  
El equipo de BAPRO resolvió la vulnerabilidad BOLA con un validador JWT custom en el backend. Este lab demostró que esa misma lógica es una capacidad nativa del gateway.

  

    
AspectoSolución custom en el backendSolución nativa en API Connect

    
Dónde vive la lógicaEn el microservicio — acoplada al código del backendEn el Assembly del gateway — independiente del backend

    
Qué pasa si cambia el IdPHay que modificar el validador en el backendSe cambia el OAuth Provider en APIC — el Assembly no cambia

    
Visibilidad y auditoríaLos rechazos 403 quedan en logs del backend — dispersosTodos los eventos de autorización quedan en el gateway — centralizados

    
Aplicabilidad a otras APIsHay que replicar el validador en cada microservicioLa misma Policy Sequence se reutiliza en cualquier API del catálogo

  

  

    Evolución — IBM Verify SaaS
    En este lab usamos el OAuth Provider nativo de APIC. Sin embargo, de requerir funcionalidades más avanzadas (por ej. gestión de consentimientos) se reemplazaría ese provider por IBM Verify como Authorization Server externo. Los cambios en el Assembly serían mínimos: solo se agrega una política Validate JWT con el JWKS URI de Verify. El Set Variable → Switch → Throw no cambia.
  


  
  
Troubleshooting

  
Errores conocidos que pueden aparecer durante el despliegue o las pruebas de la API, con su causa y forma de resolverlos.


  
"Empty root level API security is not a secure practice."

  
Este error aparece al publicar el Producto si el YAML de la API tiene un Security Requirement vacío {} junto al requerimiento real.

  

    Causa Al agregar el Security Scheme desde la UI, el API Studio a veces inserta una entrada vacía en el array security del YAML además de la entrada correcta.
  

  

    Solución Ir a API editor → ícono Source y verificar que el bloque security tenga exactamente una entrada:


    security:
  - saldos-oauth:
    - saldos:read


    Eliminá cualquier línea - {} que aparezca antes o después. Guardá y volvé a publicar.
